> Це переклад для ознайомлення. Офіційний документ — `ARCHITECTURE.md`.

## 1. Іменування файлів і папок

### 1.1 CamelCase папка = Компонент

Папка з назвою у CamelCase — це **реальний UI-компонент**.

- Повинна містити `.svelte` файл з **такою ж назвою**
- Має чітко визначений публічний API: props, events, slots
- Назва описує **що це є** — ніколи де воно знаходиться в DOM

```
ActionButton/
  ActionButton.svelte

Collapser/
  Collapser.svelte

JobManagerPanel/
  JobManagerPanel.svelte
```

### 1.2 kebab-case папка = Група

Папка в kebab-case — це **не компонент**. Це простір для групування.

- НЕ повинна містити `.svelte` файл з такою ж назвою
- Існує лише щоб об'єднати семантично споріднені компоненти
- Назва — чіткий іменник в однині або множині (детальніше в Розділі 3)

```
fields/
buttons/
modals/
```

### 1.3 TypeScript файли

| Призначення | Конвенція |
|---|---|
| Утиліти | `kebab-case.ts` |
| Stores | `something.store.ts` |
| Типи / інтерфейси | `kebab-case.ts` |

## 2. Як правильно називати компонент

### Головне правило

Назва компонента повинна відповідати на питання: **"Що цей компонент рендерить?"**

Вона НЕ повинна відповідати на питання: "Де він знаходиться в DOM?"

### Чому це важливо

Компонент існує щоб бути повторно використаним. Те, що він зараз знаходиться в хедері або в адмін-панелі — це збіг поточного використання, а не його ідентичність. Якщо компонент використовується в трьох різних місцях, назва основана на локації буде хибною в двох із них.

### Погано — назва за розташуванням в DOM

```
record/header/buttons/FavoriteEntityButton.svelte   ✗  (описує позицію в DOM)
admin/layouts/BaseLayout.svelte                     ✗  (описує секцію сторінки)
record/search-filter/FilterGroup.svelte             ✗  (описує позицію в DOM)
```

### Добре — назва за ідентичністю

```
buttons/FavoriteEntityButton/FavoriteEntityButton.svelte   ✓
FavoriteEntityButton/FavoriteEntityButton.svelte           ✓
FilterGroup/FilterGroup.svelte                             ✓
```

### Чіткість важливіша за стислість

Назва повинна бути однозначною навіть без контексту папки. Якщо розробник бачить назву компонента в імпорті — він одразу повинен розуміти що це.

- `Button` — занадто загально ✗
- `ActionButton` — зрозуміло: кнопка що запускає дію ✓
- `FavoriteEntityButton` — зрозуміло: кнопка для додавання в обране ✓

Префікси `Base`, `Common`, `Generic` — слабкі. Використовувати лише для справжніх абстрактних базових компонентів, які ніколи не рендеряться напряму.

## 3. Правила групування

### 3.1 Що таке група?

Група — це kebab-case папка, яка об'єднує компоненти зі спільною **семантичною ідентичністю** — тобто всі вони є екземплярами одного *типу речей*.

Правильна назва групи:
- **Один іменник**
- **Семантична**: описує що компоненти *є*
- **Не структурна**: не описує як вони побудовані або де відображаються

**Правильні назви груп:**

| Назва | Що означає |
|---|---|
| `fields/` | Компоненти що відображають або редагують поле даних |
| `buttons/` | Інтерактивні компоненти-тригери |
| `modals/` | Компоненти-діалоги поверх основного контенту |
| `tables/` | Компоненти табличного відображення даних |
| `charts/` | Компоненти візуалізації даних |

**Неправильні назви груп — структурні терміни:**

| Назва | Чому неправильно |
|---|---|
| `containers/` | Будь-що може бути контейнером |
| `wrappers/` | Будь-що може бути обгорткою |
| `layouts/` | Розмито — яких layouts? |
| `helpers/` | Смітник з ввічливою назвою |
| `common/` | Нічого не означає само по собі |
| `others/` | Ніколи неприйнятно |

Структурні терміни описують ЯК компоненти побудовані, а не ЩО вони є. Група з структурною назвою неминуче почне поглинати непов'язані компоненти і з часом стане безглуздою.

### 3.2 Дозрівання групи — коли її створювати

**Не створюй групу передчасно.**

Групу слід створювати лише якщо виконані ВСІ три умови:

1. Є **мінімум два** компоненти, що належать до неї
2. Їхня спільна ідентичність виражається **одним чітким іменником**
3. Групування було б **одразу очевидним** будь-якому розробнику

Якщо не можеш назвати групу з одним впевненим іменником — група ще не дозріла. Залиш компоненти пласкими.

### 3.3 Поодинокі компоненти лежать пласко

Компонент, для якого ще немає природної групи, лежить безпосередньо в `components/`:

```
components/
  Collapser/
    Collapser.svelte
  DataQualityPanel/
    DataQualityPanel.svelte
  fields/
    BoolField/
    TextField/
```

Це не проблема. Плаский список поодиноких компонентів — це **чесна структура**, яка відображає реальний стан проєкту. Це набагато краще ніж штучна група створена лише щоб уникнути плаского списку.

Коли з'являється другий компонент з явно спільною ідентичністю — групу можна виділити:

```
// До: існує лише Collapser
components/
  Collapser/
    Collapser.svelte

// Після: з'явився TreeCollapser — тепер група виправдана
components/
  collapsers/
    Collapser/
      Collapser.svelte
    TreeCollapser/
      TreeCollapser.svelte
```

Група народжується з реальності, а не з передбачень.

### 3.4 Суб-компоненти

Якщо компонент має дочірній компонент, що **використовується виключно всередині нього** і не має потенціалу для самостійного reuse — цей суб-компонент лежить всередині батьківської папки:

```
Admin/
  Admin.svelte
  RebuildDatabaseModal/       ← приватний для Admin, ніде більше не використовується
    RebuildDatabaseModal.svelte
```

Якщо суб-компонент використовується або може бути використаний в інших контекстах — його потрібно винести на відповідний рівень в `components/`.

## 4. Внутрішня структура компонента

```
ComponentName/
  ComponentName.svelte        ← обов'язково
  types/                      ← TypeScript типи та інтерфейси
    some-type.ts
  utils/                      ← чиста логіка, без Svelte імпортів
    some-util.ts
  SubComponent/               ← лише якщо є виключно приватним для цього компонента
    SubComponent.svelte
```

- UI логіка та реактивність: `.svelte`
- Чиста / обчислювальна логіка: `utils/`
- Типи та інтерфейси: `types/`

---

## 5. Структура верхнього рівня

```
src/
  lib/                        ← багаторазове ядро застосунку
    components/               ← UI компоненти (правила цього документа тут)
    core/                     ← конфіг, ACL, інтеграція з фреймворком
    stores/                   ← глобальні та спільні Svelte stores
    types/                    ← глобальні TypeScript типи, згруповані за доменом
    helpers/                  ← чисті утиліти (без Svelte, без stores)
  routes/                     ← точки входу для сторінок, тонкі, без reusable логіки
  styles/                     ← глобальні стилі, CSS змінні, reset
  main.ts                     ← лише bootstrap застосунку
```

Примітка: `lib/helpers/` — технічний простір для чистих функцій, а не компонентна група. Правило проти розмитих назв груп стосується `lib/components/`, а не технічних просторів верхнього рівня `lib/`.

## 6. Коротко: що можна, що не можна

### Можна
- Називати компоненти за тим **що вони є**, а не де відображаються в DOM
- Залишати поодинокі компоненти пласкими в `components/` поки не дозріє реальна група
- Створювати групу лише коли назва — один впевнений іменник і є мінімум два члени
- Класти суб-компоненти всередину батька лише якщо вони суворо приватні

### Не можна
- Групувати компоненти за позицією в DOM, секцією сторінки або візуальною областю
- Використовувати структурні назви груп: `containers`, `wrappers`, `layouts`, `common`, `others`
- Створювати групу для одного компонента "на всякий випадок"
- Використовувати `Base`, `Common`, `Generic` як префікси назви компонента якщо це не справжній абстрактний базовий компонент
- Класти бізнес-логіку в `.svelte` — виносити в `utils/`
- Імпортувати з `routes/` всередині `lib/`
